# GPUemu Test Harness (`TestHarness.efi`)

A lightweight, automated testing harness running natively in the EDK2/UEFI guest environment for GPUEMU.

The test harness provides automated functional and regression testing for the multithreaded software rasterizer, compute pipeline, SIMD/SIMT shader execution, texture samplers, and VRAM management.

---

## 1. Quick Start

### Running Tests via Host Scripts
You can launch QEMU and run tests directly from your host terminal using [`scripts/run.sh`](../../scripts/run.sh):

```bash
# Execute all discovered tests
./scripts/run.sh TestHarness

# Run a subset of tests using wildcard patterns
./scripts/run.sh TestHarness --test-case=raster.*
./scripts/run.sh TestHarness --test-case=compute.*
./scripts/run.sh TestHarness --test-case=*blend*

# List all available tests without executing
./scripts/run.sh TestHarness --test-list

# Dry run (walk through tests without executing GPU commands)
./scripts/run.sh TestHarness --test-dryrun
```

### Running Tests in UEFI Shell
Once inside the UEFI shell (which automatically mounts and opens `FS0:`), invoke the EFI application directly:

```
FS0:\> TestHarness.efi
FS0:\> TestHarness.efi --test-case=raster.blend.*
FS0:\> TestHarness.efi --test-list
```

## 2. CLI Options

| Flag | Description | Example |
|---|---|---|
| `--test-case=<pattern>` | Filter test cases by name using standard wildcards (`*`, `?`) | `--test-case=raster.*` |
| `--test-list` | Display all registered test cases and their descriptions | `--test-list` |
| `--test-dryrun` | Simulate test execution without invoking GPU workloads | `--test-dryrun` |
| `--help` / `-h` | Display usage instructions and options | `--help` |

## 3. Directory Layout

```
UEFI/TestHarness/
├── app.c                       # UEFI Entrypoint, CLI parsing, test runner, timers & reporting
├── harness.h                   # Core test definitions, assertion macros, and return statuses
├── TestHarness.inf             # EDK2 module build definition (sources autogenerated)
├── test_registry.h             # [AUTOGENERATED] Test forward declarations
├── test_registry.c             # [AUTOGENERATED] Static dispatch table of test nodes
│
├── cases/                      # Test cases organized by domain
│   └──  <domain>/
│       └── <test>
│
├── fixtures/                   # Modular domain-specific fixtures
│   ├── fixtures.h              # Fixture header & macro declarations (GPU_RASTER_TEST, etc.)
│   ├── common_fixture.h        # Base fixture structure & VRAM allocator trackers
│   └── <specific>              # Specifc fixtures for different domains
│
└── res/                        # Shared resources decoupled from fixtures
    ├── res.h                   # Umbrella resource inclusion header
    └── shaders/                # Precompiled shader bytecode headers
        └── <shader.h>
```

---

## 4. Writing New Tests

Tests follow a strict naming convention: `test-<domain>.<subsystem>.<case>` (e.g. `test-raster.blend.alpha`).

New `.c` files placed anywhere in `cases/` are **automatically discovered** during build without manual registry edits.

---

## 5. Status & Assertion Macros

| Macro | Description |
|---|---|
| `GPU_ASSERT(Condition, Msg)` | Fails the test with message `Msg` if `Condition` is FALSE |
| `GPU_ASSERT_EQ(Actual, Expected)` | Asserts equality between two values; prints actual vs expected on failure |
| `return GPU_TEST_PASS();` | Marks the test as successfully passed |
| `return GPU_TEST_FAIL("Reason");` | Explicitly fails the test |
| `return GPU_TEST_SKIP("Reason");` | Skips execution (e.g. pending feature development) |
| `return GPU_TEST_NOT_SUPPORTED("Reason");`| Marks test as unsupported by current hardware/driver |

---

## 6. Dynamic Discovery & Build System

The test harness uses a Python auto-discovery engine ([`tools/gen_test_harness.py`](../../tools/gen_test_harness.py)):

1. **Macro Extraction**: The tool parses [`fixtures/fixtures.h`](fixtures/fixtures.h) and [`harness.h`](harness.h) to dynamically discover all test declaration macros matching `#define <NAME>(FuncName, PathStr, DescStr)`.
2. **Case Scanning**: It scans all `.c` files in `cases/` for test declarations.
3. **Registry Generation**: It emits [`test_registry.h`](test_registry.h) and [`test_registry.c`](test_registry.c), and synchronizes the `[Sources]` section of [`TestHarness.inf`](TestHarness.inf).
4. **EDK2 Integration**: [`scripts/build_edk2.sh`](../../scripts/build_edk2.sh) runs `gen_test_harness.py` automatically before invoking the EDK2 build.

To manually re-generate the registry:
```bash
python3 tools/gen_test_harness.py
```
